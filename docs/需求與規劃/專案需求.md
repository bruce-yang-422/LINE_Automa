# LINE OA 對話紀錄與通知專案

專案名稱：`line-oa-archive`

## 目標

以本機 Python 程式串接 LINE OA，透過 Cloudflare Tunnel 提供對外 HTTPS 連線，實現對話紀錄與自動通知。

## 全站後台與 SaaS 方向（2026-09-30）

首期範圍確認為 **LINE 多 OA 管理**，同時支援「一個組織多個 LINE OA」與「一個人多個 LINE OA」。個人使用者透過「我的工作區」管理 OA，不必建立公司／組織；同一平台帳號可另依授權加入組織。每個 OA 的聯絡對象、憑證、內容工作與額度分開，先選工作區再選 OA。其他通訊平台及通用外部服務連接器不列本期；天氣與公司報表等 LINE 內容模組保留。詳細規劃見 SaaS 筆記第 10.2 節。

### 聯絡對象與後台使用者分開

- 管理介面採 Tailwind CSS 主題：先選組織，再切換人員與權限、發送範圍、可用模組；新建資料預填目前組織。
- 人員列提供設定授權／編輯角色，未完成發送授權顯示待設定；授權對話框即時顯示已選範圍與報告數。
- 帳號支援搜尋與主要角色篩選；新帳號表單提供角色說明，進階 LINE 綁定選填。後台不設「一般聯絡對象」角色，舊資料已於 2026-10-01 移除。
- Tailwind 使用本機編譯與既有主題色票，保留後端權限、站內登入及手機操作；所有文字至少符合 AA。

- 聯絡對象只透過 LINE 一對一聊天室或群組收取報告與通知，不需要建立後台帳號。
- 後台供平台管理員、組織管理員，以及需要發報告／通知的發送人員使用。
- 小組長、部門主管、專案主管是職務稱呼，不直接等同組織管理員；使用「發送人員」權限，避免因需要發送就獲得整個組織的管理權。
- 使用者已確認：發送人員依指定的部門／專案／群組授權，可同時負責多個範圍；分別限制可用模組、報告與聯絡對象，不能僅靠前端隱藏資料限制權限。所有授權仍須在各自組織內驗證，不能藉範圍名稱跨組織存取。
- 聯絡對象的組織／部門／分組與個人報告分配，獨立於登入帳號設定。新個人報告直接選擇同組織的 LINE 個人聯絡對象；舊網站帳號連結仍相容，編輯儲存後改為直接綁定。
- 保留既有資料及帳號，不將任何帳號自動升級為組織管理員。多組織帳號需按各組織有效授權選擇可登入範圍。
- 只在 LINE 收訊的人不建立後台帳號；「一般聯絡對象」角色、帳號與成員資格已於 2026-10-01 移除，歷史操作紀錄保留。管理員的唯讀視角預覽改用發送人員。
- 平台管理員在「組織管理」建立／停用發送範圍並設定發送人員授權；新帳號預設無發送、報告或天氣模組授權，也無可用報告或收件範圍。
- 部門範圍動態比對同組織的部門分類；專案勾選一至多個個人／群組；群組範圍指定一個 LINE 群組聊天室。多範圍取聯集，但必須同時符合報告原有組織／部門／個人收件限制。
- 發送人員可上傳自己的素材、發送文字／多格式圖片及獲授權報告、建立及取消本人預約；不能修改聯絡對象分類、帳號、組織、來源或授權。
- 發送人員只能查看本人在目前組織的工作，且全部對象仍在有效範圍內；直接查詢工作 ID、重複提交同一 ID 也套用相同限制。取消預約只允許本人工作。
- 組織模組與個人模組授權須同時成立；天氣額外需明確勾選天氣報告。既有組織管理員保留整個組織的管理範圍。
- 預約逐筆送出前重查帳號、成員資格、組織模組、個人授權、範圍啟用狀態、聯絡對象分類與報告授權，失效時取消該筆傳送。此功能不包含檔案變更觸發推送。

如後續啟用「檔案更新即推送」，建議採以下設計；此功能尚未實作，也未啟用任何自動發送規則：

- 每條規則明確選定組織、模組、報告來源或資料夾篩選條件，以及指定的一對一發送對象／群組；資料夾內檔案不得自動猜測發送對象。
- 一般操作優先選擇已登記的報告來源；監控的是服務所在電腦的檔案，不是戶外登入裝置的本機資料夾。
- 確認寫入完成、檔案穩定且可解碼後才建立內容快照；同次產出造成多個變更事件時合併處理。
- 以內容 SHA-256 判斷版本，僅時間變化或相同內容覆蓋不重複推送；需明訂首次啟用、服務重啟及離線期間更新的處理方式。
- 規則可先暫停／試跑，正式啟用時顯示對象及數量；送出前重新驗證操作者、組織、模組與聯絡對象授權。
- 記錄觸發來源、檔案版本、快照、聯絡對象與逐筆結果；結果不明不得無條件重送。保留現有手動立即發送及單次預約流程。

## 對話紀錄

- 使用 Cloudflare Tunnel 提供本機 Bot 的 Webhook 連線入口。
- 接收並記錄 LINE OA 收到的群組與一對一對話訊息。
- 使用本機 SQLite 資料庫儲存對話紀錄，預設檔案為 `line-oa-archive/data/line_archive.db`，不需要資料庫帳號、密碼或獨立服務。

## 媒體保存、Hash 命名與訊息引用

本節為媒體保存功能的需求與設計規劃，**尚未實作**。目前 `line-oa-archive/data/line_archive.db` 會保存文字；圖片、影片、語音及檔案只留下訊息類型、訊息 ID、來源與時間，沒有下載檔案本體。這是目前程式的功能範圍，不是 SQLite 不能儲存二進位內容。

### 保存方式

- 檔案本體放在本機媒體目錄，資料庫保存檔案資訊及訊息關聯。
- 採用「**完全相同的檔案只存一份，每則訊息分別保存並引用該檔案**」。
- 以檔案內容的完整 SHA-256（64 位十六進位字元）作為一般儲存名稱，不截短 Hash。
- 建議路徑：`line-oa-archive/data/media/<Hash 前兩碼>/<接續兩碼>/<完整 SHA-256>.<判定的副檔名>`。
- 媒體目錄不納入 Git，也不直接放進目前對外公開的 `published-images/`。
- LINE 提供依訊息 ID 下載媒體的 API，但不保證保存期限，因此需收到後盡快下載；歷史訊息只有 ID 時，不保證還能補回檔案。[LINE 官方說明](https://developers.line.biz/en/docs/messaging-api/receiving-messages)

### Hash 與時間的分工

「時間＋Hash」可以作為檔名，但相同內容在不同時間收到就會產生不同檔名；時間也不會提高 SHA-256 的抗碰撞能力。因此一般實體檔案以 Hash 命名，**每次傳送與接收時間保留在訊息資料中**。

- 分別保留 LINE 事件時間、系統接收時間、下載完成時間，統一用 UTC；介面再依使用者時區顯示。
- 下載給使用者時，可提供「時間＋原始檔名」作為顯示檔名，不必改動實體儲存名稱。
- 原始檔名屬於每次收到附件的資訊：相同內容可能由不同人以不同檔名傳送，不應只有一個共用原始檔名。

### 重複訊息與檔案引用

| 情況 | 處理方式 |
| --- | --- |
| 使用者轉傳、再次傳送或忘記已傳過 | 不同訊息 ID 各建一則紀錄；內容相同時引用同一份檔案 |
| 同一檔案出現在不同聊天室 | 保留各自的傳送者、聊天室、時間及權限；可以共用實體檔案 |
| LINE 重送同一個 Webhook | 相同訊息 ID 不重複建紀錄或下載工作 |
| 外觀相同，但重新壓縮／轉檔／修改中繼資料 | 位元組不同時另存；本階段不做視覺相似或感知 Hash 去重 |
| 某則訊息收回或附件被刪除 | 依保存政策移除該訊息的存取／引用；有其他有效引用時保留共用檔案 |

例如訊息 A、B、C 分別於不同聊天室或時間傳送同一張圖片：資料庫保留三則訊息、三個附件關聯，實體圖片一份。收回訊息後的紀錄顯示與保留期限仍需在正式規劃時決定。

### 碰撞與不同檔案格式

- 相同內容產生相同 Hash 是正常去重；不同內容產生相同 Hash 才是碰撞。
- SHA-256 碰撞在理論上可能，意外碰撞機率極低；設計上仍不假設絕對不會發生。
- Hash 計算的是完整位元組，不包含檔名或副檔名。JPG 與 PDF 等不同格式也有理論碰撞可能。
- 只將 `.jpg` 改名為 `.png`，檔案內容與 Hash 都不變，實際格式也不會因此改變。
- 同一張圖片真的轉成 JPG 與 PNG，位元組不同，Hash 通常不同，應分別保存。
- 格式應結合檔案內容／簽章與必要的格式解析判定，記錄來源 MIME 供核對，不單靠使用者副檔名。無法確定格式時保存為未知類型，避免錯誤預覽。

去重判定順序：

1. 將下載內容寫入暫存檔，串流計算 SHA-256 與實際位元組大小。
2. 依 Hash 查找既有檔案候選。
3. 比較大小；不同就不是同一份內容。
4. 大小相同時，分塊逐位元組比對完整內容，確認一致才共用。
5. 若 Hash 相同但大小或內容不同，另存為 `<Hash>_<獨立識別碼>.<副檔名>`，記錄碰撞／完整性異常；**不得覆蓋原檔**。既有檔案也可能損毀，需重新驗證後診斷。

### 資料結構與背景處理草案

| 資料 | 建議保存欄位 |
| --- | --- |
| 媒體檔案 | 獨立 `asset_id`、SHA-256、實際大小、判定格式、相對路徑、完成時間、完整性狀態 |
| 訊息附件關聯 | 訊息 ID、`asset_id`、該次原始檔名、來源 MIME、引用狀態 |
| 下載工作 | 訊息 ID、待下載／下載中／完成／失敗／來源已失效、嘗試次數、錯誤摘要 |

- 訊息來源、傳送者及時間沿用訊息紀錄，不由共用檔案取代。
- `asset_id` 作為關聯鍵；SHA-256 建索引供查找，不設為唯一主鍵，以容納異常碰撞的不同檔案。
- 下載工作先持久化再由背景處理，避免下載大影片阻塞 Webhook 回應；限制大小、逾時與重試次數，並處理來源內容尚未備妥或已失效。
- 並行下載相同檔案時，需以鎖定／交易協調比對與發布；完整下載後才發布完成檔，避免半成品或互相覆寫。
- 檔案與資料庫須設計中斷恢復、暫存清理及一致性檢查；清理共用檔案時再次確認沒有有效引用，也沒有進行中的工作。
- Hash 不是密碼或下載授權。預覽與下載須先核對使用者對所屬訊息／聊天室的權限，不能只憑 Hash 取得檔案。

### 待驗收案例

- [ ] 不同聊天室收到完全相同內容，兩則訊息都存在，只有一份實體檔案。
- [ ] 相同內容搭配不同原始檔名，仍去重且保留每次原始檔名。
- [ ] 相同 Webhook 重送，不新增重複訊息／工作。
- [ ] 同時收到相同附件，不覆寫檔案或留下不一致引用。
- [ ] 模擬相同 Hash 但不同內容，兩份檔案都保留並標示異常。
- [ ] 副檔名與實際內容不符時，不依副檔名錯誤判定格式。
- [ ] 刪除一個引用不影響其他訊息；無引用且符合保存政策時才清理。
- [ ] 無聊天室存取權者，即使知道 Hash 也不能預覽或下載。
- [ ] 下載中斷、來源失效及服務重啟能保留可追蹤狀態，不把不完整檔案標示為完成。

## 圖片與自動通知

- 使用 Python 產生 PNG 圖片，由本機 Python 圖片服務提供存取。
- 透過 Cloudflare Tunnel 提供圖片的 HTTPS 網址。
- 由 Python 呼叫 LINE Messaging API，使用圖片網址發送圖片訊息。
- 支援公告與表單提醒。
- 每日 Python 數據處理完成後，發送通知給指定業務人員。

### 第一階段手動圖片測試

- 透過根目錄 `Send-WeatherReport.ps1`，傳送 `D:\Tools\ai_weather_report\output\weather_report.png`。
- 支援一對一、測試群組或兩邊各一張；同類型有多個聊天室時，必須明確指定發送對象 ID。
- 圖片發布為獨立 PNG 快照，透過既有 Tunnel 網域的 `/images/` 路徑讀取；不開放任意檔案或目錄清單。
- 使用本機 `.env` 的 `LINE_CHANNEL_ACCESS_TOKEN` 推送，與接收驗證用的 Channel secret 分開。
- 先驗證圖片公開可讀，再呼叫 LINE API；不自動重送；新增單次預約由本機服務持續檢查執行。

### 多人聯絡對象與天氣訂閱

- 支援幾十位個人及群組，不需在 `.env` 手動維護各個 ID。
- 透過 Webhook 自動建立 SQLite 聯絡對象名單；管理員可更新 LINE 名稱、設定備註及勾選多位對象。
- 已實作背景名稱快取：收到使用者／群組事件並取得 ID 後，自動查詢 LINE 顯示名稱或群組名稱；啟動時也補查既有名單。背景每 2 秒檢查待查項目，成功快取 24 小時，失敗從 15 分鐘開始退避重試、最長 24 小時。查詢不阻塞訊息保存；手動備註保持不變且優先顯示，可用「更新 LINE 名稱」提前刷新。LINE 未提供可查詢資料時可能仍無名稱；舊式多人聊天室不支援群組名稱查詢。尚未收到任何事件的對象無法預先查名。
- 個人私訊「訂閱天氣」「取消訂閱」「我的訂閱」「幫助」管理自己的天氣訂閱，群組訂閱由管理員設定。
- 支援一次性勾選發送與天氣訂閱名單發送，保留每位對象的結果，避免重複提交或自動重送。
- 管理服務監聽 `127.0.0.1:18475`，只接受本機連線；本機由控制台開啟。其他電腦（含同辦公室）一律經 `https://line-admin.stack-base.com` 以站內帳號密碼登入，再由後端驗證權限。
- `Send-WeatherReport.ps1 -Target subscribers` 可在報告產生後發送給訂閱名單；每日排程另行設定。

### 三層角色與公司模組隔離（2026-09-30 已實作）
